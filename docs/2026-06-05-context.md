## Nex Protocol Notes

Sources read:

- `https://nightfall.city/nex/in/m15o/notes/nex-and-small-net.txt`
- `https://nightfall.city/nex/info/station-guide.txt`
- `https://nightfall.city/nex/info/specification.txt`
- `https://0x1d107.xyz/nex.html`

Nex is a very small protocol for distributed document retrieval, inspired by
Gopher and Gemini.

Protocol shape:

- Servers should listen on TCP port `1900`.
- A client connects, sends a path/selector, receives text or binary data, and
  the server closes the connection.
- No state is retained.
- Empty paths and paths ending in `/` can be treated as directories.
- Directories use plain text; lines beginning with `=> ` are links.
- Links can be absolute or relative.
- The spec includes `../nexlog/` as an example relative link.
- Documents are returned as-is.
- There is no TLS in the protocol.
- Nex is intended for public, read-only, low-stakes personal publishing.

The station guide frames a Nex site as a "station": a directory tree containing
plain text documents, optional `index` files, and directory maps using `=>`
links. It recommends text-first content and line lengths around 70 characters.

## Security Implications

The existing `nexd` is useful as a reference, but should not be exposed publicly
without sandboxing or patching.

Host risks:

- Path traversal: `nexd` uses `os.DirFS(os.Args[1])`; `nex-pfm` trims leading
  and trailing slashes but does not prevent selectors from escaping the served
  root. Because Nex supports relative links, the right fix is not to ban all
  `..`; it is to normalize selectors and reject resolved paths outside the site
  root.
- Symlink escape: `os.DirFS` does not provide chroot-like containment, so
  symlinks inside the served tree can point outside it.
- Hidden files: directory listings hide dotfiles, but direct requests may still
  open them unless the server rejects them.
- DoS: `nexd` starts a goroutine per accepted connection and has no read
  deadlines, connection limits, request size limits beyond `bufio.Scanner`'s
  defaults, or global concurrency controls.
- Exposure: `net.Listen("tcp", ":1900")` binds all interfaces.
- Plaintext transport: Nex has no TLS or server authentication by design.

Visitor risks:

- Traffic can be observed or modified by anyone on path.
- Clients should treat Nex content as untrusted text or binary data.
- Terminal clients such as `rex` pipe server-controlled output into tools like
  `less`, so hostile terminal escape sequences or unsafe extension handling are
  possible concerns.
- Nex avoids many web risks by design: no JavaScript, cookies, browser APIs,
  forms, or posting.

Minimum safe hosting posture for the current `nexd`:

- Run as a dedicated unprivileged user.
- Serve only a dedicated public directory with no secrets.
- Avoid symlinks or contain them with OS sandboxing.
- Use firewall rules to control access to port `1900`.
- Prefer a chroot, jail, pledge/unveil, container, or equivalent sandbox.

## Direction For A New Server

The new server should be a hardened Nex server that keeps the protocol small
while making the default hosting posture safer.

Likely design priorities:

- Strict site-root containment, including traversal and symlink handling.
- Public-content-only assumptions made explicit.
- Configurable bind address and port, with local or explicit public binding.
- Read deadlines and bounded selector length.
- Connection/concurrency limits.
- Clear directory behavior compatible with Nex relative links.
- Hidden file policy, probably reject dotfiles by default.
- Simple logs that avoid leaking unnecessary visitor information.
- Tests for path normalization, root containment, symlink behavior, hidden file
  policy, directory indexes, directory listings, and slow clients.
